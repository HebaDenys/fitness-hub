# Fitness Hub 0.3.3 — persistent Xiaomi archive and database backup v2

Development/test release. Same application ID and public TEST-ONLY signing key, versionCode 5. No Xiaomi login or automatic cloud synchronization is enabled by this release.

## What is new

- Room schema 6 adds persistent local identity, an explicitly confirmed Xiaomi subject/device binding, immutable per-metric protocol snapshots and transactional backfill checkpoints.
- The real Room committer is connected to the paginated Xiaomi reader. Matching pages replay without duplicate snapshots; interrupted passes resume from their saved boundary. Stale worker generations and changed replay pages are rejected.
- Other known subjects/devices are excluded from the selected archive. Ambiguous ownership stops the page without advancing its checkpoint. A second binding cannot silently replace the original person.
- Original metric representation, units, vendor method/estimates, validation issues and supported numeric extensions survive persistence. Content changes are retained as separate snapshots: `dataVersion` and `sn` are not falsely treated as authoritative event revisions/IDs.
- The backup controls in Insights now use an encrypted version-2 snapshot covering every column of the 19 registered domain tables. This includes food entries, custom exercises, sets/templates, full scale rows/composition and the new Xiaomi archive.
- Version-2 restore preserves IDs and relationships, adds missing rows, skips identical rows and rolls back the entire transaction on a conflicting row. It does not silently overwrite existing data.
- Backup file reads/writes are off the UI thread and bounded. Large archive text is not rendered in the form. Passphrases are masked, not placed in saved instance state, and cleared from the field after submitting.

## Backup boundaries

The new format covers database rows, NOT the entire application environment. Credentials, preferences, images and operational sync cursors are excluded. The decoded archive limit is 32 MiB, with additional cell/nesting limits. Version-2 restore currently requires the same database schema; cross-schema archive migration and conflict-resolution UI are future work.

Legacy version-1 backups remain readable and are explicitly labelled partial. They cannot recover fields never included by old software, and do not inherit version-2 idempotency guarantees. Automatic OS backup/device transfer stays opted out. Keep independent source copies; do not uninstall a build with valuable data based only on the existence of a backup button.

## Verification

The change adds tests using compiled Room DAOs/transactions and Robolectric native SQLite, including migrations from exported schemas 1–5, process reopen, concurrent replay, injected transaction failure, cancellation, full-domain backup round-trip, conflict rollback and malformed archives. One backup test also exercises API 35 in addition to API 28. These are not physical Redmi, S400 or live Xiaomi account tests. Actual execution results and CI references are recorded in `docs/PROGRESS.md` after the run finishes.

## Remaining work

The new archive is an integration prerequisite, not a live cloud feature or a completed canonical health engine. There is initially one immutable Xiaomi subject/device binding per installation; deliberate rebinding, legacy CSV/HC ownership migration, UI onboarding, authenticated transport/session storage and HC write-back remain to be implemented. Existing legacy imports are not retroactively given a verified identity.

A private-signing strategy still requires an owner decision before routine use of real Xiaomi credentials. No keys, passwords, user health exports, new mandatory server or production license have been introduced.
