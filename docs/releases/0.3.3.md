# Fitness Hub 0.3.3 — persistent Xiaomi archive and database backup v2

Development/test release. Same application ID and public TEST-ONLY signing key, versionCode 5. No Xiaomi login or automatic cloud synchronization is enabled by this release.

## Changes

- Room schema 6 adds local identity, explicitly confirmed Xiaomi subject/device binding, immutable per-metric snapshots and transactional backfill checkpoints.
- The paginated reader now has a real Room committer. Identical page replay is idempotent, interrupted passes resume, and stale worker generations or changed replay pages fail explicitly.
- Known other subjects/devices are excluded from the selected archive. Ambiguous ownership stops the page without advancing its checkpoint. A new binding cannot silently replace the original person.
- Original metric representation, units, vendor method/estimates, validation issues and supported numeric extensions survive persistence. Content changes remain separate snapshots: `dataVersion` and `sn` are not treated as proven event revisions/IDs.
- Insights uses an encrypted version-2 database backup covering every column of the 19 registered domain tables, including meals, custom exercises, sets/templates, scale composition and the new Xiaomi archive.
- Version-2 restore preserves IDs and relationships. It adds missing rows, skips identical rows and rolls back the entire import on conflict, orphaned relations or inconsistent Xiaomi identity/hash. Existing rows are not silently overwritten.
- File reads/writes are off the UI thread and bounded. Large archive contents are not rendered in the form. Passphrases are masked, excluded from saved instance state, and cleared from the field after submission.

## Recovery limits

This is database-data coverage, NOT the entire app environment. Credentials, preferences, images and sync cursors are excluded. The decoded archive limit is 32 MiB with additional cell/nesting limits. Version-2 restore requires the same database schema; cross-schema backup migration and conflict-resolution UI remain future work.

Old version-1 files remain readable and explicitly partial. They can only be restored into an empty health archive; existing exercise catalogues and local profile settings are retained. They cannot reconstruct fields never exported by old software. This restriction prevents the legacy adapter from silently overwriting an archive already in use.

Automatic OS backup/device transfer stays opted out. Keep independent source copies; do not uninstall a build containing valuable data based only on a backup button. Physical phone upgrade/transfer remains to be tested.

## Verification boundaries

New tests use generated Room DAOs/transactions and Robolectric native SQLite: migrations from checked-in schemas 1–5, process reopen, concurrent replay, injected transaction failure, cancellation, all-domain backup round-trip, conflict rollback, orphaned rows, tampering and malformed archives. Backup runs also cover API 35 as well as API 28. These are not physical Redmi, S400 or live Xiaomi-account tests. Results and exact CI references are recorded in `docs/PROGRESS.md` after the run finishes.

The first CI attempt found that old schema JSON omits `indices` on tables without secondary indices; the migration fixture reader was corrected to handle that format. All migration tests remain enabled.

## Remaining work

The new archive is an integration prerequisite, not a live cloud feature or a completed canonical health engine. It initially supports one immutable Xiaomi subject/device binding per installation. Explicit rebinding, legacy CSV/HC ownership migration, onboarding UI, authenticated transport/session storage and HC write-back remain to be implemented.

A private-signing strategy still requires an owner decision before routine use of real Xiaomi credentials. No keys, passwords, real health exports, mandatory backend or production license have been introduced.
